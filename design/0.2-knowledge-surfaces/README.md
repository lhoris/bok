# BOK 0.2 설계 — Knowledge Surfaces (지식 표현 계층)

> 입력: 오너 헌장("BOK 0.1.0 발전 방향 재설계", 2026-07), `design/01–06`, `research/_SYNTHESIS.md`, 그리고 4개 역할(현황실측·Knowledge Model·표현설계·레드팀)의 병렬 비판 검토.
> 이 문서군은 **바로 구현이 아니라 설계 산출물**이다. 헌장이 요구한 "이번 단계의 결과물"에 대응한다.

---

## 0. 한 문장 결론

> BOK 0.1.0은 이미 **하나의 Body of Knowledge(KU 코퍼스) + Context Model**을 갖췄다. 오너가 요구한 세 표현물(웹 리포트·LLM Wiki·용어사전)은 **새 저장소가 아니라, 같은 코퍼스에서 결정론적으로 파생되는 표현 계층(projection)** 으로 통합한다. 단, **표현을 짓기 전에 검증된 지식이 실재함을 증명**하고, 모든 표현은 **confidence·provenance·gap을 콘텐츠만큼 크게 드러내야** 한다.

---

## 1. 왜 재설계인가 (Context)

오너 헌장은 세 가지를 요구한다: (a) 대화형 웹 리포트, (b) LLM Wiki, (c) 초성 도메인 용어사전. 그리고 핵심 제약: **세 기능을 독립 결과물로 중복 구현하지 말고 하나의 Body of Knowledge에서 파생시켜라.**

현황 실측 결과, 0.1.0은 이 요구의 **데이터 토대는 이미 갖췄지만 표현 계층이 전무**하다:

- ✅ KU 모델(`provenance`·`confidence` 필수), `discover→context→validate→ready` 나선, `catalog.yaml`·`graph.json`·`coverage.yaml` 컴파일이 **결정론적으로 구현**되어 있다(`cli/bok.py` 983줄, LLM 호출 0).
- ❌ **렌더링 계층이 전혀 없다** — HTML/사이트 생성기 없음. 관계(`bok://…`)는 링크로 해석되지 않는 죽은 URI(백링크·인덱스 없음).
- ❌ **통합 IR 없음** — 스냅샷이 catalog+graph+coverage+리포트로 파편화. readiness는 저장조차 안 되고 매번 재계산.
- ⚠️ **glossary는 first-class kind지만 초성 인덱스 없음.**
- ⚠️ **agents/skills는 명세일 뿐 미구현** — 참조하는 skill 4개가 파일로 없고, LLM 추론 흐름 전체가 미검증(M6 예정). 현재 실제 KU는 100% `inferred`/`draft`.

→ 상세: [`00-current-state-and-gap.md`](00-current-state-and-gap.md)

## 2. 목표 아키텍처 (한 그림)

```
                     ┌─────────────────────────────────────────────┐
   discover→context→ │  Body of Knowledge  =  KU 코퍼스 (단일 원천)   │  ← 여기가 진실
   →validate→ready   │  bok/<context>/<kind>/*.md  (provenance·confidence)│
                     └───────────────────┬─────────────────────────┘
                                         │  build_model()  (결정론·순수함수·LLM 없음)
                                         ▼
                     ┌─────────────────────────────────────────────┐
                     │  Model  (in-memory)  ══serialize══▶ bok.json  │  ← 기계판독 계약
                     └───────────────────┬─────────────────────────┘
                                         │  bok render  (순수 투영, no re-derive)
              ┌──────────────────────────┼──────────────────────────┐
              ▼                          ▼                          ▼
     ① 웹 분석 리포트            ② LLM Wiki (내비/백링크)      ③ 초성 용어사전
     (self-contained HTML)      (사람 열람 + AI 항해)         (생성 인덱스)
              └───────── 세 표현물은 같은 사실·근거·confidence를 공유 (충돌 불가) ─────────┘
```

**핵심**: 어떤 표현물도 사실을 다시 계산하지 않는다. 백링크·상태·초성 버킷은 `build_model()`이 **한 번** 계산하고, 세 표현물은 그 결과만 읽는다. 그래서 셋은 구조적으로 서로 다른 말을 할 수 없다.

→ 상세: [`01-target-architecture.md`](01-target-architecture.md)

## 4. 새 설계 결정 요약 (D23–D31)

기존 `design/01–06`의 D1–D22를 잇는다.

- **D23** — 하나의 BoK, 여러 표현물. 표현물은 **단일 공유 모델(`build_model()`)** 위의 결정론적 투영이며, **어떤 사실도 표현물별로 재계산하지 않는다.**
- **D24** — 모델을 `bok/_system/bok.json`으로 물질화(기계판독 계약 + 리포트 임베드). 재생성 캐시(D20 계승), `source_digest` 스탬프, **purpose-독립 readiness만** 저장. 커밋 여부는 선택(기본 gitignore, 커밋 시 필수 pre-commit 무결성 훅). → [ADR-02](adr.md)
- **D25** — 결정론적 신규 커맨드 **`bok render`**(LLM 없음). `bok compile`이 모델/`bok.json`을 방출. `discover/context/validate/ready/assemble`의 계약은 불변.
- **D26** — **검증-전면화 원칙(Verification-Foregrounding).** 표현물은 confidence·provenance·gap을 **콘텐츠만큼 크게** 드러낼 때만 정당하다. `inferred`/`draft`를 `verified`처럼 보이게 하는 표현은 거부. **이것이 "문서 생성기가 되지 않는다"(비목표)를 지키는 가드레일.** → [ADR-05](adr.md)
- **D27** — 표현물은 **기존 축(context × kind × layer × coverage-area × confidence)의 투영 뷰**다. 새 물리 축을 만들지 않는다. 오너의 16개 Wiki 영역 = coverage-area 뷰. 용어사전은 1용어=1KU 유지 + 생성 초성 인덱스. 다의어는 기존 `context` 축으로 분리.
- **D28** — 웹 리포트: **단일 HTML 기본 + 임계 초과 시 split-bundle 폴백**. 그래프는 **자체 방출 SVG**(런타임 Mermaid 금지 — 결정론·용량). 검색은 임베디드 역색인. 소스 드릴다운은 설정형 base + 항상 복사 가능한 원시 locator.
- **D29** — 선택적 `glossary_term` frontmatter 추가. 초성은 결정론적(NFC 정규화, 19→14 겹자음 폴딩, 라틴/숫자·기호 버킷).
- **D30** — **검증 우선 시퀀싱.** 0.2.0은 *검증-중립적* 데이터 토대(모델·백링크·링크해석·초성 인덱스) + *게이트 우선* 정직한 표면(`bok view`)까지. 대화형 HTML·커밋 IR 캐시·증분 최적화는 0.3+로(임계/파일럿 게이트). 병렬로 LLM 파이프라인 성숙(유령 skill 4개 정리, 검증된 코퍼스까지 파일럿). → [ADR-06](adr.md)
- **D31** — 증분성: render/compile은 모델의 순수 함수. 증분 = KU 변경 감지 + 인덱스/백링크는 전량 재계산(값쌈). 헌장 기준 ⑦("처음부터 재생성 금지")에 대응.

## 5. 헌장 최종 기준 채점 (자기검증)

레드팀 채점을 오너 판단으로 조정한 결과. **본 설계가 채택되었을 때**의 목표 상태.

| # | 헌장 질문 | 현재(0.1.0) | 본 설계 후 | 관건 |
|---|-----------|:-----:|:-----:|------|
| 1 | 새 개발자가 더 빨리 이해? | ⚠️ | ✅* | *검증된 KU가 있을 때. D30 시퀀싱이 전제 |
| 2 | AI가 재분석 없이 지식 발견? | ❌ | ✅ | 링크 해석 + 백링크 + `bok assemble`(§04) |
| 3 | 근거 추적 가능? | ✅ | ✅ | provenance는 이미 강점, 표현물이 노출 |
| 4 | Gap·불확실성 확인 가능? | ✅ | ✅ | D26 전면화가 조건 |
| 5 | 세 표현물이 모순되지 않음? | — | ✅ | 단일 `build_model()` (D23) |
| 6 | 지식 증가해도 탐색 쉬움? | ❌ | ✅ | split-bundle + 역색인(§03), 뷰 투영(§04) |
| 7 | 전체 재생성 없이 갱신? | ❌ | ✅ | D31 증분 |
| 8 | 문서생성기를 넘어 온보딩 프레임워크? | ⚠️ | ✅ | D26 가드레일 + D30 검증우선 |

## 6. 검토 과정 (역할 병렬 비판)

이 설계는 단일 관점이 아니라 4개 역할의 병렬 검토 + 오너 종합으로 만들어졌다. 각 역할은 이전 결과를 그대로 수용하지 않고 근거를 확인하고 반대 관점을 제시했다:

- **현황 실측** — 코드 현실(설계≠구현)을 감사. "agents/skills는 명세일 뿐", "IR 없음", "렌더러 전무" 확정.
- **Knowledge Model 아키텍트** — bok.json 스키마 제안 + "단일 원천 보장은 파일이 아니라 빌더 함수" 재구성.
- **표현 설계자** — 세 표면 구체 설계 + "런타임 Mermaid 반대, 단일파일 단일모드 반대, 16영역 폴더화 반대".
- **레드팀** — "검증 안 된 코퍼스 위 표현은 시기상조", "코드 사실은 repo 스캔 베이스라인이 이김", OSS 선행 조사(mkdocs/Docusaurus/Backstage/DeepWiki), 헌장 8기준 채점.

오너는 이 중 **레드팀의 시퀀싱 반론을 최상위 제약으로 채택**하고, 표현 설계자의 구체안을 그 제약 아래 재배치했다. 자세한 상충 해소는 [ADR](adr.md).
