# 07 — 로드맵 · 0.2.0 범위 · 위험 · 검증 전략

> 이 문서가 오너의 "0.2.0에서 구현할 현실적인 범위"에 답한다. 핵심 판단: **검증 우선 시퀀싱(D30)** — 검증된 지식이 실재함을 증명하기 전에 화려한 표현을 짓지 않는다.

---

## 1. 시퀀싱 원칙 (D30) — 왜 표현보다 검증이 먼저인가

레드팀의 최상위 반론을 오너가 채택:

> BOK가 "repo에 AI 붙이기" 베이스라인(aider repomap·DeepWiki)을 이기는 유일한 지점은 **코드에 없는 암묵지 + 사람이 서명한 검증 지식**이다. 그런데 현재 실제 KU는 100% `inferred`/`draft`이고, LLM 파이프라인은 미검증(M6)이다. 검증 안 된 코퍼스 위에 예쁜 표현을 먼저 지으면, 독자가 `inferred`를 완성으로 신뢰하게 되어 **BOK가 막으려던 해악(잘못된 이해 확산)** 을 부른다.

→ 그래서 0.2.0은 **(a) 검증-중립적 데이터 토대**와 **(b) 게이트 우선 정직한 표면**까지만 하고, **(c) 비싼 대화형 HTML은 검증된 코퍼스가 생긴 뒤**로 미룬다. 병렬로 **검증 파이프라인을 성숙**시킨다.

이는 헌장과 정합한다: "기능 수를 늘리는 것보다 일관된 Body of Knowledge를 구축하는 것을 우선한다."

---

## 2. 0.2.0 범위 (현실적, 검증-우선)

우선순위 순. 각 단계는 단독으로 유용.

### P0 — 데이터 토대 (모든 표현물의 전제)
- **`bok compile → bok.json`**: 기존 catalog/graph/coverage/readiness의 순수 조인 + 계산된 백링크·dangling·stale·resolved provenance·초성 버킷. *공수 낮음(입력 이미 존재). 세 표현물을 모두 언블록.* **먼저 한다.**
- `build_model()` 공유 빌더 함수 — 세 표현물이 import(단일 원천 보장의 실체).

### P1 — 검증-중립적 표현 (검증 품질과 무관하게 BoK를 개선)
- **LLM Wiki 내비 계층(`bok render --wiki`)** — 링크 해석 + 백링크 + 루트/context/area 인덱스. 순수 마크다운 투영(HTML/JS 없음). **gain/effort 최고**: 오늘 가장 큰 공백(죽은 `bok://` URI)을 닫고, 사람 항해 + AI 그래프 조회를 동시 제공.
- **초성 용어사전** — `ku.glossary.template.md` + 컴파일러 초성 버킷팅 + `wiki/glossary/` 인덱스. 값싸고 도메인 온보딩 가치 큼.

### P1.5 — 게이트 우선 정직한 표면
- **`bok view`** — readiness·RED 영역·gap·KU별 confidence를 터미널/마크다운으로. **일부러 소박**해서 검증 상태를 숨길 수 없다. 0.2.0의 1차 "표면"(예쁜 HTML의 안전판).

### P2 — 최소 웹 리포트 (검증-전면화 집행)
- **`bok render --report`**, 단일 파일, 섹션 1–4 + 15만(요약·Coverage·Gaps·Readiness·용어사전). 자체 SVG 그래프, 역색인 검색, confidence 배지, `relative` 드릴다운. D26을 시각적으로 집행.

### 병렬 전제 (표현 P2를 게이트)
- **LLM 파이프라인 성숙**: discover→validate→**human sign-off**를 실제 브라운필드 context 1개에 파일럿 → `verified`·human-provenance KU 한 줌 확보. 이게 "예쁜 창"에 걸 "상품".
- **유령 skill 4개 정리**(파일 추가 or 참조 삭제) — 명세-실체 격차가 모든 주장을 약화시킴.

### 0.3+ 로 연기 (임계/파일럿 게이트)
- 대화형 HTML 풀 기능(섹션 5–16), split-bundle(수천 KU), `vscode`/`github` 드릴다운.
- **커밋되는 `bok.json` 캐시** — 측정된 파싱 시간이 임계(수백 ms/수천 KU) 넘을 때만. purpose-verdict 제외 유지.
- 증분 compile/render 최적화(설계는 D31로 지금, 발효는 스케일 시).
- 멀티레포 aggregator.

## 3. 위험 & 완화

| # | 위험 | 심각도 | 완화 |
|---|------|:---:|------|
| 1 | **시퀀싱 역전** — 미검증 코퍼스 위 표현이 `inferred` 신뢰를 조장 | 높음 | D30 검증 우선 + D26 전면화 + `bok view`(P1.5)를 1차 표면으로. 예쁜 HTML은 파일럿 게이트 |
| 2 | **베이스라인이 코드 사실을 이김**(repo 스캔이 더 신선) | 높음 | BOK 표현물은 **암묵지·verified·gap**에 집중. 코드 사실은 discover가 provenance와 함께 제공하되 표현물은 confidence로 차별화 |
| 3 | **doc-gen 비목표로 미끄러짐** — render가 SSG화 | 중 | D26 전면화 원칙 + 체크리스트(가짜 완성도 반려). SSG 채택 금지([ADR-03](adr.md)) |
| 4 | **단일 HTML 스케일 천장**(Allure 500MB 선례) | 중 | split-bundle 폴백 지금 설계, 발효는 4MB 임계. 자체 SVG(런타임 Mermaid 회피) |
| 5 | **`bok.json` drift**(커밋 파생물) | 중 | 기본 gitignore(drift 0), 커밋 시 필수 pre-commit 무결성 훅 + `source_digest`. purpose-verdict 저장 제외 |

| 7 | 명세-실체 격차(유령 skill) | 중 | P1.5 병렬 정리 |

## 4. 검증 전략 (이 설계가 옳은지 어떻게 아는가)

헌장 "지속적으로 검증한다"에 따라, 각 가설을 실측으로 검증:

| 가설 | 검증 방법 | 실패 신호 |
|------|----------|----------|
| bok.json이 IR로 값어치 | acme+mini-shop에서 세 표현물이 모두 bok.json만으로 렌더되는가 | 표현물이 KU를 다시 파싱해야 하면 스키마 부족 |
| 백링크가 죽은 URI 문제를 닫음 | mini-shop의 `bok://` 관계가 위키에서 항해 가능한가 | dangling 외 미해석 링크 잔존 |
| 초성 버킷 정확 | acme glossary + 한/영/숫자 혼합 픽스처로 골든 테스트 | 멱→ㅁ 등 골든 불일치 |
| 검증-전면화가 실제로 구별 | `inferred` KU와 `verified` KU를 나란히 렌더, 사람이 구별 가능한가 | 시각 구별 불가 → D26 위반, 반려 |
| 표현물 무모순 | 같은 KU가 리포트·위키·용어사전에서 같은 confidence·정의를 보이는가 | 불일치 = build_model 우회한 재계산 존재 |
| 증분 갱신 | KU 1개 수정 후 `render --changed`가 그 페이지 + 인덱스만 갱신 | 전량 재생성 or 백링크 미갱신 |

CLI(결정론)는 기존 `cli/test_bok.py` 방식(stdlib unittest, 의존성 0)으로 골든 테스트 추가. LLM 흐름은 파일럿에서 정성 평가.

## 5. 성공 기준 (기능 추가가 아니라 이해 향상)

헌장: "기능을 추가하는 것 자체를 성공으로 판단하지 마라." 0.2.0 성공 판정:

- [ ] 새 개발자가 `bok view` + wiki로 **verified 지식과 gap을 5분 내 파악**한다.
- [ ] AI 에이전트가 repo 재스캔 없이 `bok.json` 그래프로 이웃 지식을 찾는다.
- [ ] 리포트·위키·용어사전이 **같은 사실**을 말한다(무모순 테스트 통과).
- [ ] `inferred`가 `verified`처럼 **보이지 않는다**(전면화 테스트 통과).
- [ ] 파일럿 context 1개에서 **`verified` human-provenance KU 한 줌**이 실재한다.

마지막 항목이 없으면 나머지는 "빈 진열장"이다 — 그래서 P2 표현은 이것을 게이트로 한다.
