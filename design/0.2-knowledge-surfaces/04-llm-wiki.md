# 04 — LLM Wiki (내비게이션 계층)

> KU가 곧 위키 페이지다. 없는 것은 **해석·인덱스·백링크·context map**. 목표(헌장): AI가 전체 저장소를 반복 분석하지 않고 필요한 지식을 찾고, 사람과 AI가 같은 지식을 공유하며, 링크로 관계를 항해하고, 출처·신뢰도를 확인하고, 점진 갱신되며, 의미 있는 단위로 분리된다.

산출: `bok/_system/wiki/**` (파생 평면, 재생성 가능, offline/감사 위해 커밋).

---

## 1. 생성 구조

```
bok/_system/wiki/              # GENERATED by `bok render --wiki`
  index.md                     # 루트: context 목록, kind 카운트, readiness, 상위 gap
  context/billing.md           # context별: kind·layer로 그룹핑, coverage 격자, context-map
  area/data-model.md           # coverage-area별 인덱스 (= 오너의 "토픽" 브라우즈 뷰)
  area/business-rules.md
  glossary/index.md            # 초성 인덱스 (→ 05)
  graph.md                     # context map + 범례 (리포트와 같은 SVG 임베드)
  _backlinks.json              # id → inbound (bok.json에도 있으나 값싼 diff용 standalone)
```

**저작 KU는 `bok/<context>/<kind>/*.md`에 그대로 있다.** 위키는 그 위에 항해 셸을 씌울 뿐 — 옮기거나 복제하지 않는다(단일 원천).

### 1.1 링크 해석 & 백링크

`bok render`가 모든 `relations.target`/인라인 `bok://…`를 대상 KU `.md`로의 상대경로로 재작성하고, 각 KU에 **백링크 블록**을 붙인다. 저작 파일을 고치지 않기 위해 render는 **표시용 복사본**을 렌더하거나, render가 idempotent하게 소유하는 `<!-- bok:backlinks -->` 펜스 영역만 갱신한다. dangling 대상은 404가 아니라 `⚠ ledger-store (미발굴)`로 렌더 → gap으로 링크.

## 2. 오너의 16개 영역 = 새 폴더가 아니라 투영 뷰 (D27)

> 오너 예시 영역(overview·architecture·modules·screens·API·database·batch·external·domain·rules·ops·dev-env·decisions·glossary·**unverified**·references)을 폴더 트리로 만들면 `context × kind × layer`와 경쟁하는 **4번째 물리 축**이 생기고, 한 KU가 여러 영역에 속하는 taxonomy 충돌이 재현된다(`design/01` A.2가 직교성으로 피한 문제).

→ **오너의 영역은 이미 `coverage.yaml`의 arc42+TDD 영역과 거의 일치**하고, 그건 모든 KU에 붙은 facet(`coverage[].kus`)이다. 각 영역을 `wiki/area/<id>.md` **투영 페이지**로 렌더:

| 오너 영역 | 투영 원천(기존 축) | 새 facet? |
|----------|-------------------|:---:|
| overview / architecture | `layer:context/container` + `graph` | ✗ |
| modules | `layer:component` | ✗ |
| database | coverage `data-model` / `layer:data` | ✗ |
| batch / external | `depends-on`/`part-of` + provenance runtime/external | ✗ |
| domain / rules | `kind:explanation` + coverage `business-rules` | ✗ |
| decisions | `kind:explanation` + `decides` 관계 | ✗ |
| glossary | `kind:glossary` | ✗ |
| **unverified knowledge** | `confidence ∈ {unverified,inferred}` **필터** | ✗ |
| references / dev-env / ops | `kind:reference/how-to` + coverage deployment-ops | ✗ |
| **API / screens** | coverage building-blocks + **선택적 `tags:`** | △ 태그만 |

> **권장(추가가 아니라 재사용)**: coverage 영역을 토픽 인덱스로, kind/layer/context/confidence를 필터로 재사용. API·화면만 arc42 building-blocks보다 세밀하므로 reference KU에 **자유 `tags: [api]`/`[screen]`** 를 얹어 투영. 파일럿이 태그 부족을 입증할 때만 1급 `area` facet 도입.

## 3. AI는 무엇을 소비하나 — 3역할, 중복 없음

오너가 "Wiki"와 "Context Pack"을 혼동하기 쉬우므로 명확히:

| 소비자·용도 | 읽는 것 | 이유 |
|------------|--------|------|
| **AI 항해** ("멱등 키를 정의하는 게 뭐지? settlement-batch에 뭐가 의존?") | **`bok.json`** | 이미 해석된 백링크·그래프·coverage 보유. 사람용 위키 마크다운을 읽지 않음(같은 사실의 렌더 뷰 → 토큰 낭비) |
| **AI 작업** ("배치에 재시도 안전성 추가") | **`bok assemble`** → Context Pack(L1/L2/L3 + gaps + warnings) | JIT 검색. 브라우징 아님. (기존 구현) |
| **사람 열람** | **`_system/wiki/*.md`** | 사람 브라우즈 전용 표면 |

> **LLM Wiki(브라우즈)와 `bok assemble`(검색)은 하나의 BoK 모델의 두 소비 경로**(`design/01` B.5). 위키 = "그래프를 걷고 페이지를 읽기", assemble = "이 작업에 필요한 최소 팩". 둘은 `bok.json`을 공유하고 내용을 복제하지 않는다. **에이전트 기본 루프 = 작업엔 `assemble`, 항해엔 `bok.json` 그래프 조회, 사람용 위키 마크다운은 안 읽음.**

이것이 헌장 "AI가 전체 저장소를 반복 분석하지 않고 필요한 지식을 찾는다"의 답이다: 죽어있던 `bok://` URI가 **해석된 그래프 + 백링크**가 되어, 에이전트가 repo 전체를 재스캔하는 대신 `bok.json`에서 이웃을 조회한다.

## 4. 증분 갱신 (D31)

`bok render --wiki --changed`: 마지막 스냅샷 이후 소스 md가 바뀐 KU만 재렌더(mtime/hash를 `render.lock`에), 그다음 **백링크·index·area·glossary 페이지는 bok.json에서 전량 재계산**(값싼 순수 투영이라 낡을 수 없음). 기존 pre-commit `bok compile` 훅에 `bok render`를 추가.

> "처음부터 재생성"이 아니라 "바뀐 KU만 + 값싼 인덱스 전량 재계산" — 헌장 기준 ⑦ 대응.
